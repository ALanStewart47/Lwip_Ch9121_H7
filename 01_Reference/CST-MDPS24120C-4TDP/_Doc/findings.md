# 审查发现与证据

## 审查口径

- `确定`：可由当前源码、编译器诊断或明确规格直接证明。
- `高概率`：存在清晰失效路径，但依赖运行时条件或外部输入。
- `待确认`：取决于硬件、上位机、协议或产品期望行为。

## 项目概览

- MCU/工具链：STM32G431，Keil MDK 工程 `MDK-ARM/STM32G431.uvprojx`。
- 主运行结构：CubeMX 初始化 GPIO、DMA、ADC2、USART2、SPI2、SPI3、
  TIM3/TIM6/TIM7、IWDG，随后进入应用初始化和轮询主循环。
- 已编入工程的自有模块包括 App、Protocol、部分 BSP、W5500 与 RTT。
- 源码目录中若干文件未编入当前 Keil target，至少包括：
  `app_slave_control.c`、`app_slave_processor.c`、`app_spi_bridge*.c`、
  `app_pvd.c`、`bsp_spi_bus.c`、`bsp_uart_dma.c`。审查需以 uvprojx 的实际
  编译清单为准，避免把停用/样例代码当成在产路径。
- 当前唯一处于本项目内的既有 Git 修改为
  `App/src/app_adc_handle.c`：在 ADC DMA 启动前新增单端校准并在失败时进入
  `Error_Handler()`。后续会分别评估当前代码和 Git 基线行为。
- 未在当前目录及向上两级发现 `AGENTS.md`。

## PDF 规格摘要

- PDF 共 16 页，V1.0，版本记录日期 2025-02-02；文件元数据标题却为
  `CST-BPS24120CIP6-4TD`，与用户给出的 `CST-MDPS24120C-4TDP` 型号不一致，
  需判断是模板元数据遗留还是文件/产品对应错误。
- 固件相关章节：产品规格（p4）、面板/按键（p5-p7）、模式与触发时序
  （p8-p11）、通信协议（p12-p15）。
- 可编程模式宣称最多 64 步，支持软触发/CH1 外触发、单步/连续两种工作模式。
- p12-p15 同时描述旧 ASCII、扩展 ASCII、全功能二进制协议，需逐项对照解析器。
- 额定规格（p4）：4 路恒压、DC 24 V、总电流 5 A、单路最大 3 A、
  总功率 120 W、PWM 117 kHz、0-255 级亮度。
- 外触发（p4/p8/p10）：DC 12-24 V、约 5.6 mA，普通模式是电平触发，
  频闪模式是上升沿触发，延迟 `<15 μs`。
- 频闪脉宽（p7/p8）：0-999 ms，说明书声称误差 `±0.02 ms`。
- 可编程模式（p9）：最多 64 步；软/CH1 外触发；单步/连续；执行期间忽略
  其他触发；每步在相机输出端产生 12 V、约 0.5 ms 同步脉冲。
- 面板（p5-p7）：亮度 0-255、脉宽 0-999；异常时 E 灯点亮并显示
  `E___X` 错误码。
- 串口（p12）：RS232，19200-8-N-1。网口默认 IP `192.168.1.208`、
  TCP/UDP 端口（文档只写“端口号”）6600，IP 可由软件设置。
- 常规 ASCII（p12）：亮度 `S[A-D][0000-0255]#`，模式 `T[H/L]#`。
- 扩展 ASCII（p13）：`$` 写、`@` 读、两位功能码、可变数量通道、`#` 结束，
  成功 `$`/`@...#`，失败 `*`。
- 全功能 HEX（p14-p15）：`CA` 单通道、`CB` 多通道、BCC 校验；
  错误状态 0=成功、1=不支持、2=通道越界、3=数据越界。
- 说明书存在内部文字矛盾/瑕疵：p14 称“扩展协议”且“两条指令”，p15 又称
  “扩展协议只有1条”且标题/正文一处把多通道指令写成“单通道指令”。
  因此代码与协议工作簿可能比 PDF 更接近真实协议定义。

## 候选问题

- 待验证：`Error_Handler()` 为关中断后死循环，而 IWDG 已初始化；
  若 IWDG 在该路径仍运行，预期会复位而非永久死锁，需结合初始化时序判断。
- 待验证：应用源码同时存在不同 SPI/UART 实现及重复 HAL callback 名称，
  但当前 target 似乎只选入其中一套；工程清单是安全性的关键组成部分。
- 待验证（启动可靠性）：IWDG 在 `bsp_Init()` 前启动，按 LSI≈32 kHz、
  prescaler=8、reload=4095 估算超时约 1.0 s；初始化中有三次 300 ms 延时
  及一次 `bsp_system_open_display(2000)`。需确认显示函数是否在 2 s 内喂狗，
  否则上电会循环复位。
- 待验证（启动地址）：应用在 `HAL_Init()` 前把向量表设为 Flash+0x3800，
  同时 linker/bootloader 的镜像基址与 VTOR 写入实现需一致，否则中断入口错误。
- 待验证（阻塞风险）：`printf` 重定向使用 `HAL_UART_Transmit(..., 0xFFFF)`，
  DEBUG_MODE=1；若 UART 状态异常或在时间敏感路径打印，最长可能阻塞约 65 s，
  远超约 1 s 的看门狗周期。
- 已排除“开机动画不喂狗”：动画每次约 500 ms 延时前会喂狗，通常不会触发
  约 1 s IWDG。但函数存在确定性时长偏差：参数 2000 ms 被除以 4 后循环
  6 次，实际约 3000 ms，而非 2000 ms。
- 启动镜像和向量表基址一致：scatter 文件与 `APPLICATION_POSADDR_A`
  均为 `0x08003800`。不过 `NVIC_SetVectorTable()` 名义上只是设置 VTOR，实际还
  DeInit RCC/HAL、关闭 SysTick、清除全部 NVIC，再重新开全局中断；当前只在
  `main()` 最早期调用尚可工作，但接口副作用很大，未来复用风险高。
- 软件定时器到期和 1/10 ms 调度使用单 bit flag；主循环阻塞期间多次到期会
  合并成一次处理，不会补做。这会让 10 ms 过流/按键任务和 50 ms 喂狗调度
  产生不可控抖动，需结合主循环最坏执行时间评估。
- 高风险候选（过流保护）：检测函数每 10 ms 调用一次，连续计数条件使用
  `++err_cnt > 500`，名义动作时间约 5.01 s，且主循环阻塞会进一步延迟。
  对 24 V/单路 3 A/总 5 A 产品，这个纯软件动作延迟是否可接受必须由硬件
  限流/保险丝方案确认。
- 高风险候选（过流阈值定义不一致）：实际比较的是按浮点宏算出的
  `GB_OCP_VALUE_MAX`（4 路配置约 217 ADC count），而头文件另有注释为
  “0.25 V / 1.5*310”的 `ADC_OVER_CURRENT_VALUE=465`，后者完全未使用。
  这可能导致误保护或保护点偏离设计值，需用采样电路增益/分流电阻确认。
- 确定性健壮性问题：ADC 校准和 DMA 启动中，当前未提交版本只检查校准返回值，
  仍未检查 `HAL_ADC_Start_DMA()` 结果；若 DMA 未启动，缓冲区保持 0，
  过流保护会静默失效且系统继续运行。
- `fliter_calucation(a,m)` 固定读取从 `a[m/2]` 到 `a[m/2+9]`，没有长度
  前置条件；当 `m < 18` 左右会越界。当前编译路径暂未发现调用，属于潜伏 API
  缺陷而非在产失效。
- PWM 规格核对通过：TIM3 时钟约 170 MHz、ARR=1452，对应约 117 kHz，
  与 PDF 一致（`USER_PWM_FREQ` 名称实际表示周期计数而不是频率）。
- 已排除“外触发完全无业务响应”：4 个 EXTI handler 在 HAL 处理后直接调用
  `bsp_trig_callback()`；`bsp_trig_init_in_falling()` 注册的回调最终进入
  `trig_callback()`。空的 `HAL_GPIO_EXTI_Callback()` 只是当前架构未使用。
- 规格/实现待确认：PDF 把频闪描述为“上升沿有效”，代码的隔离输入在 MCU 侧
  配置为下降沿且把低电平解释为有效。光耦可能反相，因此不能仅凭边沿字面判错，
  需要原理图或示波器确认。
- 频闪执行存在两套路径：在产 EXTI 走 `bsp_trig_fast_handle()`，会开灯、计数、
  打开相机输出并启动两类定时器；`fast_trig_isr()` 当前未见调用，属于易混淆
  的残留实现。
- 确定性内存安全缺陷：`bsp_prog_trig_set_current_step(0)` 通过检查后执行
  `step - 1`，把 `uint8_t programmable_step` 设为 255；随后多个执行函数直接
  用它索引 64 项 `prog_table`，可越界读写/产生异常输出。需追踪协议是否允许
  传入 0。
- 确定性内存安全缺陷：`bsp_prog_trig_insert_table()` 对满 64 步未拒绝；
  `memmove(&table[idx+1], ..., (total-idx)*sizeof(row))` 会写到数组末端之外。
  同时函数先无条件 `prog_total_steps++`，随后在 `<64` 时再次递增，因此一次
  插入通常把总步数加 2。当前未发现生产调用点，属于明确但可能未启用的 API bug。
- 明确规格偏差：PDF 规定可编程模式每步相机同步脉冲约 0.5 ms；代码按
  programmable unit 输出 1 ms 或 0.1 ms，没有 0.5 ms 分支。
- 高概率单位错误：连续模式的行间隔总是
  `programmable_interval * 10000`，没有像脉宽一样在 `PROG_UNIT_100US`
  时乘 1000；若“单位”同时适用于行间隔，则 100 µs 模式的间隔会放大 10 倍。
- 待确认：可编程模式 `bsp_cam_output_enable()` 只驱动 CAM_OUT_1；若产品要求
  每路灯对应各自相机输出，则当前实现不符。PDF p9 用单数 OUT+/OUT-，p10 又
  列出 4 路相机信号，文档本身不够明确。
- `bsp_prog_trig_set_current_step()` 在生产协议回调中直接使用，调用返回值被忽略；
  因而“step=0 → 255 → prog_table 越界”并非纯死代码。仍需确认各协议解析器是否
  在进入公共回调前把步号最小值限制为 1。
- 协议公共层对 recipe、TriggerSource、Line_number 多处先减 1 再索引，局部
  没有防 0；安全性高度依赖上层解析器统一校验，后续作为协议审查重点。
- 重大远程输入风险（UDP 配置）：CST_W5500 分支把网络包中的 21 字节设备名
  完整复制到 `uint8_t devname[21]`，随后直接 `strlen(devname)`；若 21 字节
  均非 0，`strlen` 会越界读栈，得到的长度又用于复制到 21 字节全局字段，
  可继续造成越界写。该路径仅要求收到长度 285、标志/MAC 匹配的 UDP 配置包。
- 高风险候选（TCP 接收错误）：`recv()` 的有符号错误返回值被直接存入
  `uint16_t tcp_rec_len`，未判断 `<=0` 就作为 `memcpy` 长度；若在
  `getSn_RX_RSR()>0` 后发生 socket 错误，负错误码会变成约 655xx，导致
  300 字节缓冲区之间的大规模越界复制。
- UART DMA 的启动/重启返回值均被忽略；发送遇到 HAL_BUSY/ERROR 也静默丢弃。
  在多个命令连续到达或 DMA 异常时，上位机可能收不到响应且无错误状态。
- UART 查找接口在 uart number 不存在时仍会解引用空 `uart_p`；当前主路径只用
  已注册 UART0，但回调/API 缺少局部防护。
- Router 的同步等待回复把协议层 `tx_len` 复制到 `s_pending_reply_buf[SUM_SIZE]`，
  原有上限检查被注释。若协议层任何路径返回长度大于 `SUM_SIZE`，会发生溢出；
  需结合 `SUM_SIZE` 和所有响应构造函数确认。
- SPI 回复处理默认底层总是返回完整 26 字节：函数未先验证 `data!=NULL`、
  `len==26` 就读取 payload、`data[len-1]`、日志中的 `data[0..9]`，并把 `len`
  字节复制到 26 字节局部数组。当前 SPI 调用的期望响应长度确为 26，但异常
  回调长度将直接形成越界读写，建议作为边界防御项。
- `map_channel()` 对 global channel 0 会做无符号下溢并映射成 slave index 63；
  是否可达取决于单/多通道路由在调用前的通道校验，待继续确认。
- 已确认网络编译分支是 `CST_W5500=1`，TCP 端口 6600 与 PDF 一致；
  UDP 配置缓冲区 290 字节，前述 285 字节设备名漏洞位于实际启用分支。
- Router 单通道对 channel=0 的少数命令视为广播；其他 channel=0 经无符号下溢
  后被判为无效 slave 并回送本地协议层。多通道的 0/无效通道也会被归入本地；
  最终是否拒绝依赖协议层。
- 确定性 C 未定义行为候选：Router 组本地多通道帧时使用
  `tmp[k++] = bcc_xor(tmp, k)`，同一完整表达式中修改并读取 `k`，求值顺序未受
  保证；不同编译器/优化级别可能算错 BCC。应由编译器警告/构建进一步确认。
- 高风险协议边界候选：`analysis_command()` 按实际接收长度逐字节扫描，但各旧/
  新协议 handler 直接读取 `uart_buf[i+1]...i+N`，没有接收剩余长度参数。
  截断帧或在缓冲区末尾放置协议头可越过 300 字节 `rx_buffer` 读取；需对具体
  handler 的最大偏移和写路径继续核对。
- 重大、可由串口/TCP 触发的协议缺陷：`CB` 多通道帧直接信任 1 字节
  `channel_counts`，先创建 VLA `Channel_Data data[channel_counts]`、计算 BCC
  并转换数据，完全没有“剩余接收长度/最大通道数”前置检查。短帧
  `CB <cmd> FF` 即会按 768 字节解析 300 字节协议缓冲区，并在栈上分配约
  2 KiB（Keil 下 `unsigned int`/对齐后），造成越界读和栈风险。
- 重大、可远程触发的可编程帧缺陷：`CC Set_Programmable_data` 信任 16 位
  `channel_count`，在验证 `channel_count<=4` 之前就按
  `12 + channel_count*2` 读取 BCC。恶意大计数可导致大范围越界读/HardFault。
- 重大索引下溢：可编程协议只检查 recipe/TriggerSource/Line_number
  “是否大于最大值”，不拒绝 0；下层立即减 1 后索引
  `[1][1][64]...` 数据结构。合法 BCC 的 0 值可直接越界读写。
- 同类单通道缺陷：读命令只拒绝 `channel>4`，允许 channel=0；多个
  `Get_Controller_Data()` 分支用 `channel-1` 索引 4 项数组，可越界读取。
  某些写命令把 0 定义为广播，因此需要按“具体命令是否允许 0”校验，不能统一
  只检查上限。
- `Read_ProgTable_data_cmdhandle()` 在 CRC、recipe/TriggerSource/Line_number
  校验之前就调用公共回调读取数据，错误帧也能先触发非法索引和状态变化。
- `package_tx_buffer()` 向固定 300 字节回复缓冲区追加数据时没有容量检查；
  单次接收包含多个命令、且响应总长大于请求总长时可能溢出。需要用协议组合
  测试或静态枚举确认最大扩张比。

## Flash / 掉电保存补充

- 确定性越界/未定义行为：`FlashParams_t` 按当前字段布局为 26 字节，但保存和读取都按
  `(sizeof + 7) / 8 = 4` 个 doubleword，即 32 字节操作。保存时会越过对象读取
  6 字节未初始化栈填充，恢复时会越过对象写入 6 字节。当前 ARMCC 栈帧看起来留有对齐空间，
  未必立刻覆盖返回地址，但换编译器/优化或局部布局后不安全，Flash 中也会混入不确定字节。
- 掉电事务不完整：DATA、PROG、BAUD 三类记录都没有 CRC/版本；有效标志在正文之前写入。
  掉电导致部分写入时，下次启动仍可能把残缺记录判为有效。
- PVD 的 `PWR_PVD_MODE_IT_RISING` 不再列为问题：STM32 的 PVDO 在 VDD 低于阈值时置位，
  所以电压跌落会形成 PVDO 上升沿；当前选择与掉电检测方向一致。阈值 Level 6 约 2.9 V，
  仍需靠板上储能确认是否足够完成后续擦写。
- PVD 中断回调里执行 Flash 擦除/编程，且 `bsp_SaveBaudData()` 每次都先擦除一页。
  这在供电已经下降时既耗时又依赖剩余储能，失败返回值还被全部忽略。
- `bsp_SaveFlashData()` 本身不擦 DATA 页，依赖启动恢复后立即擦除形成“一次性预擦除页”；
  这套假设在异常复位、Flash 操作失败或 PVD 重入时没有状态保护。
- `SavePowerDown_enable()` 按 doubleword 把值写在 `ENABLE_SAVE_ADDR + 8`，对应读取函数却从
  `ENABLE_SAVE_ADDR + 2` 取值。当前调用链大多被注释，属于确定但休眠的持久化 bug。
- 链接脚本把应用区声明为 `0x08003800 + 0x20000`，其终点超出 128 KiB 器件 Flash，
  且允许链接器把代码/常量放进从 `0x0801C800` 开始的参数保留页。现有 bin 约 60–73 KiB，
  当前增量构建 map 显示 load region 实际末端约 `0x080155D8`，尚未碰撞；但工程没有任何
  linker 级保护，后续增长约 29 KiB 就可能开始覆盖 W5500/参数页而构建仍然成功。

## 构建验证

- Keil target `STM32G431` 增量构建成功：0 error、0 warning。
- 当前镜像：RO 72,592 B，RW+ZI 12,856 B，总 ROM 72,736 B（约 71.03 KiB）。
- 0 warning 不能排除本报告中的越界/未定义行为；ARMCC 5 默认诊断未报告
  Router 表达式求值顺序、协议长度信任和 Flash 结构尾部越界。
- 当前启动文件仅保留 `Stack_Size=0x400`（1024 B），但 Keil 静态调用图给出的最大合法调用链
  已达 1168 B，且标注还存在函数指针未知量。最大路径可由 TCP/UART 的 `Set_DataSave`
  触发；`bsp_prog_trig_save_to_flash()` 单函数栈占用 808 B。栈会越过保留区进入相邻 heap，
  在中断嵌套或 heap 正在使用时可破坏内存。
- heap 仅 512 B；ARMCC 把 `MultiChannel_cmdhandle()` 的运行期数组实现为 `malloc/free`。
  外部 `channel_counts` 无上限，申请失败后代码不查 NULL 就写入，构成可远程触发的
  HardFault；这比单纯“约 2 KiB VLA”更确定。

## 通信、定时与状态机补充

- TCP 被当作“一个 `recv()` 就是一帧”处理，没有跨接收调用的粘包/拆包缓存。TCP 是字节流，
  即使一条短命令也允许被拆成两次接收；当前路径会把前半帧立即交给协议层，既会误解析，
  又会触发已发现的截断帧越界读取。
- UART DMA 发送直接引用协议层静态 TX 缓冲区或 Router 的全局 50 字节缓冲区；发送开始后
  没有锁定/复制，下一条 UART/TCP/SPI 回复可以在 DMA 尚未完成时改写同一内存。
  同时 `HAL_UART_Transmit_DMA()` 的 BUSY/ERROR 被静默忽略，会产生回复乱码或直接丢回复。
- TIM7 配置为 170 MHz / 1700，再设置 `Period=10`；STM32 定时器周期是 ARR+1，实际中断约
  110 us。SPI 接口注释称 1 tick=100 us，而常量又命名为 `*_MS`；例如 delay=2、timeout=20
  实际约为 0.22 ms/2.2 ms。需要确认从机协议真正要求的是 tick 还是毫秒。
- 可编程连续模式的后续步骤若脉宽为 0，会调用 `bsp_tim2_start_cc(..., delta=0, ...)`。
  比较值被设为当前 CNT，通常已经错过该比较点，要等 32 位 TIM2 绕回（约 429 s）才回调；
  期间 `prog_busy` 保持工作状态，序列近似卡死。首步骤对 0 有特殊处理，后续步骤没有。
- 心跳频率 `switch` 的 MEDIUM 分支缺少 `break`，先赋 20 s 后立即落入 LOW/default 改为 10 s；
  中等频率实际与低频率相同。
- 可编程同步 ACK 校验低字节使用
  `data[4] == g_prog_sync__interval & 0xFF`，按 C 优先级会先做相等比较再按位与。
  当 interval >255 时，即使从机正确回显低字节也无法通过该条件。
- 从机扫描遇到某个 ID 连续失败就直接停止，不继续扫描更高 ID；后续又用
  `1..g_found_slave_count` 假设从机地址连续。若产品允许地址空洞，会漏设备并错误映射在线状态。
- SPI 底层读取完成后已经注释掉帧头校验；扫描和心跳回调也不校验 BCC，仅参数同步/Router
  各自校验。偶发 SPI 位错误可能把无效帧判为在线/扫描成功，校验策略不一致。
- 波特率页面会调用 `bsp_SaveBaudData()`，但实际编译 target 中唯一的 `bsp_CheckBaud()` 调用点
  位于未编译的 `bsp_uart_dma.c`；当前启动流程固定先以 19200 初始化，Flash 恢复又注释了
  `uart_baud_gear`。因此面板修改的波特率重启后不会恢复。
- 外部触发进入可编程模式时，公共 EXTI 回调已把输入计数加 1，
  `bsp_prog_trig_exec()` 又对 TRIG1 加 1；因此可编程外触发计数每次增加 2，
  软触发则只增加 1。
- `enabled/Channel_Switch` 只在普通模式控制循环里被检查；频闪和可编程路径会直接
  `bsp_light_on()`，禁用通道仍可能点亮。若 Channel Switch 是全模式总使能，这是明确功能/安全 bug。
